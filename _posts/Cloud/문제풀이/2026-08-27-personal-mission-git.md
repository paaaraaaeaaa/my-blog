## 오늘의 상황

수업에서는 팀이 함께 쓸 블로그를 기획했다. 자율 실습은 내가 혼자 쓸 블로그를 준비하는 시간이다. 열다섯 문제가 모두 같은 소재(내 블로그)를 쓰기 때문에, 문제마다 "무엇을 만들지"는 고민할 필요가 없고 연습할 것은 Git 명령 하나뿐이다.

- 내일은 이 블로그를 진짜 인터넷 주소로 배포한다. 오늘 적어 둔 글 계획이 그대로 쓰인다.
- 막혔을 때: 힌트3까지 봐도 풀리지 않으면 AI에게 물어본다. 단 "답을 알려줘"가 아니라 "왜 안 되는지 설명해줘"로 물어야 한다. 답을 받으면 그 순간은 넘어가지만, 다음 문제에서 또 막힌다.
- Lv.1 여섯 문제는 서로 독립이다. 하나를 안 풀어도 다음으로 넘어갈 수 있다.
- 저장소는 1-1에서 만든 것을 계속 써도 되고, 문제마다 새로 만들어도 된다. 문제에 적힌 파일 이름만 맞추면 된다.
- 기본 브랜치 이름은 `main`일 수도 `master`일 수도 있다. `git branch`를 쳐서 `*`가 붙은 이름을 먼저 확인한다.
- 오늘 만든 팀 조직 저장소는 건드리지 않는다. 자율 실습은 전부 내 개인 계정에서 한다.
- 명령을 치기 전과 후에 `git status`를 친다. 오늘 배운 것 중 가장 쓸모 있는 습관이다.
- 화면이 멈춘 것처럼 보이면 `q`를 누른다. 기록을 보여주는 화면이 열린 것이다.

# Lv.1 기본 변형 (6문제)

수업에서 친 것을 값·조건만 바꿔 다시 치는 문제들이라 서로 독립적이었다.

## 1-1. 내 블로그 저장소를 만들고 첫 글 3편 계획하기

**문제**: `my-blog-plan` 폴더를 저장소로 만들고, 그 안에 `posts.txt`를 만든다. 내가 진짜 쓰고 싶은 첫 글 3편의 제목과 한 줄 요약을 적는데, 한 편을 적을 때마다 커밋을 한 번씩 해서 커밋 3개가 쌓이게 한다. 다 되면 GitHub에 올리고, 커밋 메시지는 무엇을 왜 바꿨는지 알 수 있게 자기 말로 쓴다.

**시도한 방법**
```
mkdir my-blog-plan          # 폴더 만들기
cd my-blog-plan             # 폴더로 이동
git init                    # Git 저장소 초기화

(posts.txt에 1편 제목·요약 작성)
git add posts.txt           # 스테이징(올릴 준비)
git commit -m "1편: 부트캠프 첫 주에 겪은 것 계획"   # 커밋(저장)
(2편 추가 작성)
git add posts.txt
git commit -m "2편: ... 계획 추가"
(3편 추가 작성)
git add posts.txt
git commit -m "3편: ... 계획 추가"
# 위 add와 commit 과정을 3편까지 총 3번 반복

git remote add origin <깃허브_빈_저장소_주소>   # 원격 저장소 연결
git branch -M main          # 기본 브랜치 이름을 main으로 통일
git push -u origin main     # 깃허브로 밀어 올리기
```

⚠️ **막힐 수 있는 지점**: 로컬 기본 브랜치 이름이 `master`인 채로 `git push -u origin main`을 치면 에러가 난다. `git branch -M main`으로 이름을 먼저 맞추거나, `git push`에 실제 브랜치 이름을 그대로 써야 한다.

🟢 **확인 방법**: `git log --oneline`을 치면 3줄이 나온다 / GitHub에서 새로고침하면 `posts.txt`가 보인다 / 커밋 메시지만 읽어도 어느 글을 추가한 커밋인지 구분된다.

**막혔던 점 / 배운 점**

🔴 커밋을 3개로 나누었는데, 세부적인 내용을 적지 않고 빈 칸으로 냅뒀더니 어떤 내용을 commit 하고 적용했는지 구분이 잘 가지 않았다. 그래서 세부 내용을 상세하게 까진 아니더라도 간단하게 어떤 부분을 수정했는지 적어야 인식하기 편하다는 것을 배웠다.

## 1-2. status만 보고 무엇이 담길지 맞히기

**문제**: 파일 3개를 서로 다른 상태로 만든다 — `todo.txt`(새로 만들고 그대로 둠), `about.txt`(고치기만 하고 스테이징에 올리지 않음), `posts.txt`(고쳐서 스테이징에 올림). 이 상태에서 `git status`를 찍고 "지금 커밋하면 무엇이 담기는가"를 파일 3개 각각에 대해 먼저 답을 적은 뒤, 실제로 커밋해서 맞았는지 확인한다.

**시도한 방법**
```
(todo.txt 새로 생성 - 그대로 둠)
(about.txt 수정 - add 안 함)
(posts.txt 수정 후 git add posts.txt)
git status
→ 예상 답 작성: todo.txt(Untracked) 안 담김 / about.txt(Changes not staged) 안 담김 / posts.txt(Changes to be committed) 담김
git commit -m "posts.txt만 반영"
git log --oneline -1  # 실제로 들어간 파일 개수 확인
```

💡 **핵심 개념**: `git status` 출력은 세 덩어리로 나뉘고, 색으로도 구분된다(초록/빨강).
- `Changes to be committed:` → `posts.txt` (지금 커밋하면 담기는 파일)
- `Changes not staged for commit:` → `about.txt` (수정은 됐지만 스테이징 안 된 파일)
- `Untracked files:` → `todo.txt` (새로 만들어서 Git이 아직 추적하지 않는 파일)

**막혔던 점 / 배운 점**

🔴 git status를 통해 상태를 확인할 때, 의도와 달리 바뀌지 않아서 이런 경우에 명령어를 실행하는 순서도 중요하고, 실행 결과를 많이 확인하면 좋을 것 같음.

## 1-3. 글 초안 둘 중 완성된 하나만 올리기

**문제**: 블로그 글 초안 두 개(`draft-1.txt`, `draft-2.txt`)를 한꺼번에 만든다. 1편은 다 썼고 2편은 아직 쓰는 중이라고 치고, **완성된 하나만** 커밋해서 GitHub에 올리고 다른 하나는 올리지 않은 채 내 컴퓨터에만 남겨 둔다.

**시도한 방법**
```
(draft-1.txt, draft-2.txt 작성)
git status                 # 둘 다 보임
git add draft-1.txt        # 완성된 것만 지정
git status                 # draft-1은 초록, draft-2는 빨강
git commit -m "1편 초안 완성분만 반영"
git push
```

🟢 **확인 방법**: GitHub 저장소 페이지에 초안 파일이 1개만 보인다 / 내 컴퓨터에서 `git status`를 치면 올리지 않은 초안이 여전히 목록에 남아 있다.

**막혔던 점 / 배운 점**

🔴 git add를 전체 다 적용하는 방법만 학습을 한 상태였어서, add를 파일별로 구분하여 적용할 수 있는 방법이 대해 배웠다.

## 1-4. 아직 남에게 보이기 싫은 것 막기

**문제**: 블로그 저장소는 공개다. 그런데 올리고 싶지 않은 파일이 두 개 있다 — `secret-draft.txt`(아직 남에게 보이기 싫은 글 초안), `my-memo.txt`(나만 볼 개인 메모). `.gitignore`를 만들어 두 파일 모두 GitHub에 올라가지 않게 하고, 그 상태에서 다른 파일을 하나 커밋해 push한다.

**시도한 방법**
```
(secret-draft.txt, my-memo.txt 생성)
echo "secret-draft.txt" >> .gitignore
echo "my-memo.txt" >> .gitignore
git status              # 두 파일이 안 보여야 성공
git add .gitignore
git commit -m ".gitignore 추가: 비공개 파일 제외"
(다른 파일 하나 수정 후 커밋)
git push
```

⚠️ **주의할 점**: `.gitignore` 파일 이름이 실수로 `.gitignore.txt`가 되지 않도록 확인. 파일 하나당 한 줄씩 적는다.

🟢 **확인 방법**: `git status`에 두 파일이 나타나지 않는다 / GitHub엔 `.gitignore`는 있고 두 파일은 없다 / 내 컴퓨터에는 파일이 그대로 있다(삭제되는 게 아니다).

**막혔던 점 / 배운 점**

🔴 .gitignore 작성 후에도 파일이 계속 추적되고 있어서 원인을 살펴봤다. 그 이유는 이미 커밋된 적 있는 파일이라 그런 것이었음. 상태를 주기적으로 확인할 필요성을 느꼈다.

## 1-5. 브랜치를 만드는 순서 바꿔보기

**문제**: 블로그 소개 문구(`about.txt`)를 고치는 같은 작업을 두 가지 순서로 해보고 결과를 비교한다.
- **가**: 브랜치를 먼저 만들고 → 그 브랜치에서 `about.txt`를 고치고 커밋
- **나**: 기본 브랜치에서 `about.txt`를 먼저 고치고 → 커밋하기 전에 브랜치를 만들고 → 그 브랜치에서 커밋

두 경우 모두 기본 브랜치로 돌아갔을 때 파일 내용이 어떻게 되어 있는지 확인하고, 무엇이 같고 무엇이 달랐는지 한 문단으로 적는다.

**시도한 방법**
```
git branch                              # * 표시로 기본 브랜치 이름 확인(main/master)

[가]
git switch -c branch-a
(about.txt 수정) → git add about.txt → git commit -m "가: 소개 문구 수정"
git switch main → about.txt 열어보기 → 내용 확인

[나]
(about.txt 수정) → git switch -c branch-b → git add about.txt → git commit -m "나: 소개 문구 수정"
git switch main → about.txt 열어보기 → 내용 확인

# 가, 나 모두 main 브랜치로 돌아가면 수정한 내용은 보이지 않는다
```

💡 **핵심 개념**: 커밋하지 않은 변경은 브랜치를 옮겨도 따라다닌다. 커밋한 변경은 그 브랜치에만 남는다.

🟢 **확인 방법**: 두 경우 모두 기본 브랜치에는 수정 내용이 없다 / 브랜치로 옮기면 수정 내용이 나타난다.

**막혔던 점 / 배운 점**

🔴 '나' 방식에서 about.txt를 먼저 고쳐놓고 브랜치를 만들었는데, 새 브랜치로 넘어가도 수정 내용이 그대로 남아있어서 "분명 아직 커밋 안 했는데 왜 새 브랜치에도 보이지?" 하고 헷갈렸다. 알고 보니 커밋하지 않은 변경은 특정 브랜치에 속한 게 아니라 그냥 작업 폴더에 떠 있는 상태라서, switch로 브랜치를 새로 파도 그대로 따라오는 거였다. 커밋을 해야 비로소 그 브랜치에 "고정"된다는 걸 몸으로 확인한 문제였다.

## 1-6. 기록을 세 가지 방법으로 읽기

**문제**: 브랜치를 만들어 블로그 글 한 편을 추가하고 기본 브랜치에 병합해서, 갈라졌다 합쳐진 기록을 만든다. 그 상태에서 아래 세 명령의 출력을 각각 확인하고, "이럴 땐 이걸 쓴다"를 세 줄로 정리한다.
```
git log
git log --oneline
git log --oneline --graph
```

**시도한 방법**
```
git branch                              # 기본 브랜치 이름 확인
git switch -c post-new
(posts.txt에 글 추가) → git add posts.txt → git commit -m "새 글 추가"
git switch main
(about.txt 수정) → git add about.txt → git commit -m "소개 문구 수정"
git merge post-new
git log --oneline --graph               # 여기서 갈래가 보인다
```

**정리 예시**
- `git log`: 커밋 메시지·작성자·날짜까지 자세히 봐야 할 때
- `git log --oneline`: 전체 흐름을 한 줄씩 훑어볼 때
- `git log --oneline --graph`: 브랜치가 갈라지고 합쳐진 모양을 눈으로 보고 싶을 때 (화면이 멈춘 것처럼 보이면 `q`)

# Lv.2 응용 (4문제)

이번 차시 개념에 첫날 배운 터미널·경로를 섞은 문제들이다.

## 2-1. 터미널만으로 블로그 글 폴더 구조 만들기

**문제**: 블로그 글이 늘어나면 월별로 폴더를 나눠 정리하게 된다. 아래 구조를 **탐색기를 쓰지 않고 터미널 명령만으로** 만든다.
```
my-blog-posts/
├─ 2026-08/
│  ├─ week1.txt
│  └─ week2.txt
├─ 2026-09/
│  └─ week1.txt
└─ readme.txt
```
각 `.txt`에 그 주에 쓸 글 제목을 한 줄씩 넣고, 저장소로 만들어 GitHub에 올린다. 폴더를 만들 때마다 `cd`로 이동해서 만들고, 절대경로와 상대경로를 모두 한 번씩 써본다.

**시도한 방법**
```
mkdir my-blog-posts ; cd my-blog-posts
mkdir 2026-08 ; cd 2026-08
(week1.txt, week2.txt 생성 후 제목 한 줄씩 작성)
cd ..                     # 상대경로로 위로
mkdir 2026-09 ; cd 2026-09
(week1.txt 생성)
cd ..
(readme.txt 생성)
git init
git add .
git commit -m "블로그 글 폴더 구조 초기화"
git remote add origin <저장소 주소>
git push -u origin main
```

🟢 **확인 방법**: GitHub에서 `2026-08` 폴더를 클릭하면 파일 2개가 보인다 / 터미널에서 `cd my-blog-posts` 후 `dir`(또는 `ls`)을 치면 `2026-08`, `2026-09`, `readme.txt`가 보인다.

**막혔던 점 / 배운 점**

🔴 `cd 파일경로`를 적으면 해당 경로로 이동한다는 사실을 알았지만, 이전으로 돌아갈 때는 `cd ..`를 이용하는 것을 배웠다. 파일명을 직접 입력한 이전 경로로는 이동이 불가능하다.

## 2-2. 에러 메시지 3종 읽고 원인 말하기

**문제**: 블로그 저장소를 만들다 보면 반드시 만나는 에러들이다. 아래 세 상황을 일부러 만들어 메시지를 직접 보고, 각각에 대해 ① 화면에 나온 문장 ② 왜 이런 일이 생겼는지 ③ 어떻게 고쳤는지를 적는다.
1. 저장소가 아닌 폴더에서 `git status`를 친다
2. GitHub 저장소를 아직 연결하지 않은 상태에서 `git push`를 친다
3. 존재하지 않는 파일 이름으로 `git add`를 친다

**시도한 방법**
```
1. cd ~/그냥폴더 && git status
   → "not a git repository" 계열 메시지
   → 원인: 이 폴더는 Git이 관리하는 곳이 아니다
   → 해결: git init으로 저장소로 만들거나, 저장소 폴더로 이동

2. (새 폴더에서) git init → git push
   → "no upstream branch" 또는 remote 관련 메시지
   → 원인: 어디로 올릴지 아직 알려주지 않았다 (커밋 여부와는 다른 문제)
   → 해결: git remote add origin <주소> → git push -u origin main

3. git add 없는파일.txt
   → "did not match any files" 계열 메시지
   → 원인: 그 이름의 파일이 실제로 존재하지 않는다(오타 포함)
   → 해결: 파일 이름을 정확히 확인하고 다시 add
```

💡 **핵심 개념**: 에러 메시지의 첫 줄을 천천히 읽으면 Git은 대부분 원인과 해결책을 함께 알려준다.

## 2-3. 혼자서 브랜치 → PR → 병합 한 바퀴

**문제**: 내 블로그 저장소에 글을 두 편 더 추가한다. 단, 한 편에 브랜치 하나씩 쓴다. 두 브랜치를 각각 PR로 열고, 자기가 리뷰 코멘트를 달고, 자기가 병합한다. 다 끝난 뒤 "오늘 수업에서 팀으로 했던 것과 무엇이 달랐나요? PR이 왜 필요한지 잘 알겠나요, 아니면 덜 알겠나요?"에 답한다.

**시도한 방법**
```
git switch -c post-3
(글 추가) → git add . → git commit -m "3번째 글 추가"
git push -u origin post-3
→ 웹에서 PR 열기 → 스스로 리뷰 코멘트 달기 → 병합
git switch main
git pull
git switch -c post-4
(반복)
```

🟢 **확인 방법**: PR 탭에 병합 완료된 PR 2개가 보인다 / 각 PR에 내가 쓴 코멘트가 달려 있다 / 기본 브랜치로 돌아가 `git pull`하면 두 글이 모두 내 컴퓨터에 있다.

**막혔던 점 / 배운 점**

🔴 팀으로 할 때는 리뷰어가 실제로 내용을 모르는 상태에서 질문하거나 다른 관점으로 의견을 줘서 도움이 됐는데, 혼자 PR을 열고 스스로 리뷰까지 다니까 형식적으로 코멘트만 다는 느낌이 들었다. 그래도 "왜 이렇게 바꿨는지"를 코멘트로 남기는 습관 자체는 도움이 됐다 — 나중에 로그만 봐도 이유가 기억났다. PR이 왜 필요한지는 여전히 팀에서 리뷰를 주고받을 때가 훨씬 크게 느껴졌고, 혼자 할 땐 "기록을 남기는 절차"라는 느낌이 더 컸다.

## 2-4. 내 조직 만들어 보기

**문제**: 오늘 조직은 팀장만 만들어 봤다. 이 문제는 전원이 직접 해보는 자리다. 내 이름으로 조직을 하나 만들고, 그 조직 안에 저장소를 하나 만들어 블로그 기획 파일을 하나 커밋해서 push한다. 그리고 개인 계정 저장소 vs 조직 저장소의 주소가 어떻게 다른지, 무엇이 같고 무엇이 다른지 표로 정리한다.

**시도한 방법**
```
1. 조직 만들기 (무료 선택지)
2. 조직 안에서 저장소 만들기 — 소유자를 조직으로 선택!
3. 내 컴퓨터에서 git clone 또는 git remote add
4. (기획 파일 작성) → git add . → git commit -m "..." → git push
5. 주소 비교:
   개인: https://github.com/<내계정>/저장소
   조직: https://github.com/<조직이름>/저장소
```

💡 **핵심 개념**: 조직 이름은 GitHub 전체에서 하나뿐이어야 한다("이미 사용 중"이면 뒤에 숫자를 붙인다). 저장소를 만들 때 소유자를 조직으로 선택해야 한다.

🟢 **확인 방법**: 조직 페이지에 내가 만든 저장소가 보인다 / 저장소 주소에 내 아이디가 아니라 조직 이름이 들어간다 / 비교 표를 3줄 이상 채웠다.

**막혔던 점 / 배운 점**

🔴 처음 정한 조직 이름으로 만들려고 했더니 이미 사용 중이라는 안내가 떠서 뒤에 숫자를 붙여 다시 만들었다. 그리고 저장소를 만들 때 소유자를 제대로 확인 안 하고 넘어갔다가 개인 계정에 만들어진 걸 뒤늦게 발견해서, 삭제하고 소유자를 조직으로 다시 선택해서 새로 만들었다. 저장소 만들 때 "소유자" 항목을 꼭 확인해야 한다는 걸 배웠다.

# Lv.3 도전 (2문제)

요구사항만 주어지고, 설계는 스스로 한다.

## 3-1. 블로그 3일치 작업을 남이 읽을 수 있게 남기기

**요구사항**: 다른 사람이 커밋 로그와 PR 목록만 보고 "이 사람이 3일 동안 블로그를 어떻게 준비했는지" 알 수 있어야 한다. 파일은 열어보지 않고서. 소재는 내 블로그로 고정이지만, 파일을 어떻게 나눌지·커밋을 어떤 단위로 쪼갤지·브랜치를 몇 개 쓸지·PR 제목을 어떻게 쓸지는 전부 스스로 정한다. 3일치라고 생각하고 만든다 — 예를 들어 1일차는 기획, 2일차는 글 초안, 3일차는 다듬기처럼. 커밋 8개 이상, PR 2개 이상이어야 한다. 다 만든 뒤, 옆 사람에게 저장소 주소를 보여주고 "이 기록만 보고 내가 3일 동안 뭘 했는지 알겠어?"라고 물어본다.

**시도한 방법 (설계)**
```
계획을 먼저 적는다:
- 1일차(브랜치 plan): 기획 관련 커밋 2~3개
- 2일차(브랜치 draft): 글 초안 커밋 3~4개
- 3일차(브랜치 polish): 다듬기 커밋 2~3개
- 커밋 메시지 규칙: "[기획] ...", "[초안] ...", "[수정] ..." 처럼 태그를 앞에 붙이기

실행:
git switch -c plan → (기획 파일들, 여러 번 커밋) → PR 열기 → 병합
git switch main → git pull
git switch -c draft → (글 초안들, 여러 번 커밋) → PR 열기 → 병합
...
```

🟢 **확인 방법**: `git log --oneline`이 8줄 이상이고, 메시지만 읽어도 날짜별 작업 흐름이 보인다 / PR 탭에 2개 이상이 병합되어 있고 제목이 구체적이다 / **옆 사람이 파일을 열지 않고 내 3일 작업을 요약할 수 있었다** ← 이것이 진짜 채점 기준이다.

**막혔던 점 / 배운 점**

🔴 커밋을 어느 단위로 쪼개야 할지 처음엔 감이 안 와서, 일단 하루 치 작업을 통째로 커밋 하나에 넣으려고 했다. 그런데 그렇게 하면 로그만 봐서는 그날 안에서 뭘 했는지 전혀 안 보일 것 같아서, "기획 파일 하나 추가", "초안 오타 수정"처럼 더 잘게 나눴다. 옆 사람에게 저장소를 보여줬더니 로그 메시지만 보고도 1일차엔 기획, 2일차엔 초안, 3일차엔 다듬기를 했다는 걸 맞혔다. 다만 PR 제목을 조금 두루뭉술하게 써서 "이 PR에서 정확히 뭘 봐야 하는지" 헷갈렸다는 피드백을 받아서, 제목에 범위를 더 구체적으로 적어야겠다고 생각했다.

## 3-2. 충돌을 세 가지 방식으로 해결하기

**문제**: 블로그 소개 문구 `about.txt`를 두고 충돌을 세 번 일으키고, 매번 다른 방식으로 해결한다.
1. 내 것만 살리기
2. 상대 것만 살리기
3. 둘 다 살리기

세 경우의 최종 파일 내용과 커밋 기록이 어떻게 달라지는지 비교해서 적고, "어떤 상황에 어떤 방식이 맞을까"를 한 문단으로 쓴다. 혼자 하는 실습이라 상대가 없으니, 브랜치 두 개를 내가 양쪽 다 맡는다고 생각한다.

**시도한 방법 (1회차 예시 — 순서를 그대로 지켜야 충돌이 난다)**
```
git branch                                  # 기본 브랜치 이름 확인
git switch -c try-1                         # 먼저 갈라진다
(about.txt 첫 줄을 A로 수정)
git add about.txt ; git commit -m "소개 문구 A안"

git switch main                             # 돌아와서 같은 줄을 다르게 고친다
(about.txt 첫 줄을 B로 수정)
git add about.txt ; git commit -m "소개 문구 B안"

git merge try-1                             # → CONFLICT!
(파일 열어 충돌 기호 지우고 "내 것만" 남기기)
git add about.txt ; git commit
```
2회차·3회차는 같은 순서로 반복하되, 충돌 해결에서 "상대 것만" → "둘 다"로 바꿔서 진행.

💡 **핵심 개념**: 충돌이 나려면 두 가지가 동시에 맞아야 한다 — ① 두 브랜치가 갈라진 뒤에 ② 양쪽 다 같은 파일의 같은 줄을 고쳐 커밋했어야 한다. 충돌 해결은 특별한 명령이 있는 게 아니라 파일을 손으로 고치는 것이다. `<<<<<<<`, `=======`, `>>>>>>>` 기호를 지우고 원하는 내용만 남기면 되고, 그 뒤 `git add` → `git commit`.

🟢 **확인 방법**: 세 번 모두 `CONFLICT`라는 글자를 화면에서 봤다 / 해결 후 파일에 충돌 기호가 남아있지 않다 / `git log --oneline --graph`에 병합 기록이 3개 보인다.

**막혔던 점 / 배운 점**

🔴 "내 것만", "상대 것만"은 충돌 기호 사이에서 한쪽 문단만 남기면 돼서 어렵지 않았는데, "둘 다 살리기"에서는 두 문장을 그냥 순서대로 붙이니 문맥이 뚝뚝 끊겨서 어색했다. 그래서 접속사를 하나 넣고 문장 순서도 살짝 바꿔서 자연스럽게 이어지도록 손을 봤다. 결론적으로 완전히 다른 내용이면 "둘 다 살리기"가 맞고, 한쪽이 실수거나 더 이상 안 쓰는 내용이면 "한쪽만 살리기"가 맞겠다는 생각이 들었다.

# 보너스 (3문제)

먼저 끝낸 사람을 위한 문제. 다 풀지 않아도 된다.

## B-1. 나쁜 커밋을 만들어 보고 후회하기

**문제**: 블로그 저장소에서 일부러 나쁜 커밋을 만든다 — 서로 관계없는 변경 5가지 이상(글 추가 + 오타 수정 + 초안 삭제 + 파일 이름 변경 + 새 폴더)을 한 커밋에 몰아넣고, 커밋 메시지는 "수정" 또는 "ㅇㅇ"처럼 성의 없이 쓴다. 그 뒤 "글 하나만 잘못 올린 걸 되돌려야 하는 상황"을 가정하고 실제로 시도해본다. 무엇이 불편했는지, 어떻게 커밋했어야 했는지를 적는다.

**시도한 방법**
```
(5가지 이상 관계없는 변경을 한꺼번에)
git add .
git commit -m "수정"

# 되돌리기 시도
git revert --no-edit <해시>
(파일들을 열어보고 무엇이 사라졌는지 확인)
```

🟢 **확인 방법**: 하나만 되돌리려 했을 때 원하지 않는 것까지 딸려온다는 것을 직접 겪었다 / "커밋을 어떻게 쪼갰어야 했는지"를 구체적인 커밋 목록으로 다시 적었다.

💡 **핵심 개념**: `git revert`는 커밋 단위로 되돌린다. 커밋이 크면 되돌리기도 크다.

**막혔던 점 / 배운 점**

🔴 revert로 되돌렸더니 글 추가만 취소하고 싶었는데 오타 수정이랑 폴더 이름 변경까지 같이 사라져서 당황했다. 파일을 다시 열어보니 잘못된 것도 아니었던 부분까지 원래대로 돌아가 있어서, 결국 그 부분만 다시 손으로 고쳐야 했다. 이번 일로 하나의 목적(글 추가, 오타 수정, 이름 변경)마다 커밋을 따로 나눴어야 되돌릴 때도 필요한 것만 골라 되돌릴 수 있었겠다는 걸 알게 됐다.

## B-2. 나만의 기록 규칙 만들고 자기 평가

**문제**: 아래 세 가지에 대해 좋은 것의 조건을 각각 3가지씩 스스로 정한다.
1. 좋은 커밋 메시지
2. 좋은 PR 제목과 설명
3. 좋은 리뷰 코멘트

그리고 오늘 내가 실제로 남긴 기록(개인 블로그 저장소 + 팀 블로그 저장소)을 내가 만든 기준으로 점수를 매기고, 낮은 항목을 어떻게 고칠지 적는다.

**시도한 방법**
```
기준 정하기 (예시):
- 좋은 커밋 메시지: ① 무엇을 바꿨는지 동사로 시작 ② 왜 바꿨는지 한 줄 추가 ③ 20자 이상
- 좋은 PR 제목: ① 무슨 기능인지 명확 ② 범위가 하나로 좁혀짐 ③ 리뷰어가 뭘 볼지 예상 가능
- 좋은 리뷰 코멘트: ① 무엇이 문제인지 명시 ② 왜 문제인지 설명 ③ 어떻게 고칠지 제안 포함

자기 평가:
git log --oneline (오늘 커밋 목록) → 기준별로 점수 매기기
```

🟢 **확인 방법**: 기준 9개(3×3)를 구체적인 문장으로 적었다("좋게 쓴다" 같은 건 기준이 아니다) / 오늘 내 커밋 5개 이상을 실제로 평가했다 / 낮은 점수를 받은 것에 대해 고쳐 쓴 예시를 적었다.

💡 **핵심 개념**: 기준은 판정 가능해야 한다. "구체적으로 쓴다"(X) → "무엇을 왜 바꿨는지 둘 다 들어간다"(O).

**막혔던 점 / 배운 점**

🔴 실제로 점수를 매겨보니 급하게 쓴 커밋 메시지 하나가 그냥 "수정"이라고만 적혀 있어서 내가 정한 기준 3개를 다 못 채웠다. 왜 그랬는지 생각해보니 그때는 실습 진도를 따라가는 데 급급해서 메시지를 신경 쓸 여유가 없었던 것 같다. 그 커밋을 다시 쓴다면 "about.txt 소개 문구를 더 간결하게 수정"처럼 무엇을 왜 바꿨는지 넣어서 다시 적었을 것 같다.

## B-3. 안전망 실험 — 날리고 되살리기

**반드시 개인 블로그 저장소에서만 진행. 팀 저장소에서는 절대 하지 않는다.**

**문제**: 아래 세 가지를 각각 실험하고, 무엇이 남고 무엇이 사라지는지 표로 정리한다.
1. `git reset --soft` / `--mixed` / `--hard`를 같은 상황에서 각각 실행하고 `git status` 비교
2. `--hard`로 커밋을 날린 뒤 `git reflog`로 되살리기
3. 글을 쓰다 만 상태를 `git stash`로 치워두고 다른 브랜치에서 꺼내보기

**시도한 방법**
```
1. 실험용 커밋 3개 쌓기
   git reset --soft HEAD~1  → git status → 기록
   (되돌리고) git reset --mixed HEAD~1 → git status → 기록
   (되돌리고) git reset --hard HEAD~1 → git status → 기록

2. git reflog → commit: 이라고 적힌 줄의 해시 찾기
   git reset --hard <그 해시>

3. (글 수정) → git stash → git switch 다른브랜치 → git stash pop
```

🟢 **확인 방법**: 세 가지 reset의 차이를 표 하나로 정리했다(커밋 / 스테이징 / 내 파일 3열) / 날린 커밋이 실제로 되살아났다 — `git log`에 다시 보인다 / stash한 작업을 다른 브랜치에서 꺼내는 데 성공했다.

💡 **핵심 개념**: `git reflog`는 내가 이동한 모든 기록을 보여준다. `log`와 다르다. `stash`는 브랜치에 묶여 있지 않다.

**막혔던 점 / 배운 점**

🔴 --hard로 커밋을 날렸더니 진짜로 파일 내용까지 그 이전 상태로 돌아가 있어서 신기하면서도 무서웠다. reflog를 쳤을 때 이동 기록이 생각보다 많이 남아 있어서 원하는 커밋을 한 번에 못 찾고 몇 줄 위아래로 훑어봐야 했다. stash는 처음 써봤는데, 다른 브랜치로 옮겨서 pop 했을 때 하던 작업이 그대로 나와서 신기했다 — 커밋하지 않고도 작업을 잠깐 치워둘 수 있다는 걸 알게 됐다.
