> 이 글은 오늘 수업의 **팀 미션**을 기록한 devlog입니다.
> 팀마다 다른 미션(A~E)을 받았는데, 우리 팀은 미션 B를 배정받아 먼저 진행했고, 끝난 뒤 시간이 남아 다른 팀들의 미션(A, C, D, E)도 이어서 전부 풀어봤습니다.
> 문제마다 `문제 상황 → 시도한 방법 → 막혔던 점 → 해결 과정 → 배운 점` 순서로 정리했습니다.

# 오늘의 상황

오늘 수업에서는 팀 블로그의 뼈대를 잡았다. 각자 맡은 기능 기획서를 하나씩 올렸고, 대문에 걸 한 줄 소개도 정했다. 그런데 블로그를 진짜로 열기 전에 팀이 결정해야 할 것이 하나씩 남아 있었다. 팀마다 다른 숙제를 받는다고 해서, 우리 팀은 **미션 B**를 받았다.

- 수업에서 만든 팀 블로그 저장소를 그대로 쓴다. 새 조직도 새 저장소도 만들지 않는다.
- 시작 전에 전원이 `git switch main` → `git pull`로 같은 지점에 선다. 이걸 건너뛰면 미션 도중에 엉킨다.
- 미션은 강사가 팀에 배정한다. 내 팀 미션(B)만 먼저 읽고, 나머지는 공유 시간에 봤다.
- 다섯 미션 모두 브랜치 → PR → 리뷰 → 병합 한 바퀴를 돈다. 거기까지는 같고 무엇을 관찰하는지가 다르다.
- 미션에서 만드는 `*-rule.txt`는 팀 저장소에 커밋한다. 공유 시간에 그대로 쓴다.

미션 B를 끝낸 뒤 팀 회고와 팀 간 공유를 마쳤고, 시간이 남아서 다른 팀이 받았던 미션 A, C, D, E도 순서대로 다 해봤다.

# 우리 팀 미션 — 미션 B: 기획서 검수 기준을 만들고 반려해 본다

## 상황

수업에서 올린 기능 기획서 `feature-*.txt`를 모아 놓고 보니 모양이 제각각이었다. 어떤 건 담당자 이름이 없고, 어떤 건 동작 설명이 한 줄뿐이었다. 이대로 계속 쌓이면 나중에 아무도 못 읽는다. "이건 안 받는다"는 선을 팀이 정하고, 실제로 반려까지 해보는 게 이번 미션의 목표다.

- **할 일**: 기준 3개 → 일부러 어긴 PR → 반려 → 수정 → 승인
- **알아낼 것**: 판정할 수 있는 리뷰 기준은 어떻게 생겼는가
- **쓰는 개념**: Pull Request · 코드 리뷰 · 브랜치 · 병합

## 1단계 — 기준 정하기

### 문제 상황
팀이 기획서 승인 기준 3가지를 정해 `review-rule.txt`에 적고 커밋·push해야 한다. 단순히 "잘 쓴다"가 아니라 **판정할 수 있는 문장**이어야 한다는 제약이 있다. 예: "잘 쓴다"(X) → "첫 줄에 담당자 이름이 있다", "동작 설명이 두 줄 이상이다"(O).

### 시도한 방법
```
git switch main
git pull
(review-rule.txt 작성: 기준 1~3 적기)
git add review-rule.txt
git commit -m "리뷰 기준 3가지 합의"
git push
```
팀원들과 화면 공유하며 "이 기준으로 판정 가능한가?"를 서로 되물어보면서 문장을 다듬었다.

### 막혔던 점
🔴 처음 정한 기준 중 하나가 "설명이 충분해야 한다"였는데, 팀원마다 "충분하다"의 기준이 달라서 같은 기획서를 두고도 어떤 사람은 통과, 어떤 사람은 반려라고 답이 갈렸다.

### 해결 과정
🟢 기준 문장에 **숫자나 구체적 위치**(첫 줄, 두 줄 이상 등)를 넣으니 팀원 누가 봐도 같은 결론이 나오기 시작했다.

### 배운 점
💡 리뷰 기준은 "좋다/나쁘다"가 아니라 "예/아니오"로 답할 수 있어야 실제로 쓸모가 있다는 것.

## 2단계 — 일부러 어기고 반려하기

### 문제 상황
전원이 각자 브랜치에서 블로그 기능 기획서를 하나씩 더 만든다(좋아요, 구독, 임시저장, 조회수, 다크 모드 등 자유 주제). 그중 **팀 기준 3가지 중 하나를 일부러 어겨야** 한다(어느 걸 어겼는지는 말하지 않는 것이 규칙). 그다음 각자 PR을 열고, 내 오른쪽 사람의 PR을 리뷰해서(마지막 사람은 첫 번째 사람 것을 봄) 어긴 부분을 찾아 **Request changes**로 반려하고 무엇이 왜 기준에 안 맞는지 코멘트를 남긴다. 반려당한 사람은 고쳐서 다시 push → 리뷰어가 Approve → 병합.

### 시도한 방법
```
git switch -c feature-내기능
(feature-내기능.txt 작성, 기준 중 하나를 일부러 위반)
git add feature-내기능.txt
git commit -m "기능 기획서 초안 추가"
git push -u origin feature-내기능
→ GitHub에서 PR 오픈
```
리뷰 순서는 원형으로 돌아가게 정했다(1→2→3→1).

### 막혔던 점
🔴 상대방의 기획서에서 어떤 기준을 일부러 어겼는지 한 번에 못 찾았다. 세 기준을 하나씩 다시 대조해보고 나서야 "동작 설명이 한 줄뿐"이라는 걸 찾아냈다. 처음 리뷰 코멘트도 "기준에 안 맞아요"라고만 짧게 써서, 상대가 정확히 뭘 고쳐야 할지 못 알아듣고 되물어봤다.

### 해결 과정
🟢 반려 코멘트에 "왜 안 되는지"뿐 아니라 "review-rule.txt의 몇 번 기준"인지까지 인용해서 달았더니, 수정이 한 번에 끝났다.

### 배운 점
💡 Request changes는 단순 거절이 아니라 **다음 커밋을 위한 구체적 지시**여야 한다는 것. 코드 리뷰 코멘트도 하나의 "기록"이라 나중에 다시 읽어도 이해가 가야 한다.

## 3단계 — 기준 고치기

### 문제 상황
실제로 반려까지 써보니 판정하기 애매했던 기준이 있었는지 팀이 이야기한다. 있으면 문장을 고쳐 `review-rule.txt`를 다시 커밋한다.

### 시도한 방법
2단계를 실제로 겪어보고 나서야 기준의 허점이 보였다. 예를 들어 "동작 설명이 두 줄 이상"이라는 기준은 의미 없는 줄을 두 번 써도 통과가 되는 허점이 있었다 → "두 줄 이상 + 각 줄에 조건 하나씩" 식으로 보강.

### 막혔던 점 / 해결 과정 / 배운 점
🔴 **막혔던 점**: "동작 설명이 두 줄 이상"이라는 기준이 의미 없는 줄을 두 번 써도 통과되는 허점이 있다는 걸, 실제 반려 사례를 보고서야 알아챘다.

🟢 **해결 과정**: 기준 문장에 "각 줄에 조건을 하나씩 포함해야 한다"는 조건을 추가해서 다시 커밋했다.

💡 **배운 점**: 기준은 한 번 정하고 끝나는 게 아니라, 실제로 써보면서 허점을 찾아 계속 다듬어야 한다는 걸 알았다.

## 끝나고 남는 것 (체크리스트)

- [ ] `review-rule.txt`가 두 번 커밋되어 있다 — 처음 것과 고친 것
- [ ] 새 기능 기획서가 인원 수만큼 병합되어 있다
- [ ] 각 PR이 한 번씩 반려됐다가 승인됐고, "왜 기준에 안 맞는지"가 코멘트로 적혀 있다

## 팀 회고 (retro.txt)

팀끼리 모여 아래 네 가지를 `retro.txt`에 적어 커밋·push했다.

1. **가장 오래 막힌 순간** 하나 — 화면에 뭐라고 나왔는지 그대로 적기
2. 그때 무엇을 해서 풀었는지 — 누가 무엇을 알아냈는지도 적기
3. 우리 팀이 정한 **규칙 3줄** — 미션에서 만든 `*-rule.txt`에서 옮겨 적기
4. **다른 팀에 물어보고 싶은 것 1개**

> 팀마다 미션이 다르기 때문에, 4번이 특히 중요했다. 우리가 안 겪어본 상황을 이미 겪은 팀이 있으니까.

## 팀 간 공유

짝 팀의 저장소 주소를 받아 커밋 로그와 PR 목록만 보고 "저 팀은 무슨 숙제를 받았을까"를 추측해 한 줄로 적었다. 그다음 발표에서 실제 미션을 밝히고, 가장 오래 막힌 순간과 우리 팀 규칙 3줄을 공유했다. 마지막으로 다섯 팀이 가져온 규칙을 모아 **반 공통 규칙 5줄**을 정하고, 각 팀 저장소의 `team-rule.txt` 맨 아래에 커밋했다.

# 시간이 남아서 — 다른 팀 미션도 다 풀어보기

미션 B와 팀 회고·공유까지 예정보다 빨리 끝나서, 다른 팀이 받았던 미션 A, C, D, E도 개인적으로(또는 팀원들과) 이어서 진행했다. 각 미션은 원래 그 미션을 받은 팀 저장소 구조를 그대로 흉내 내서 연습했다.

## 미션 A: 대문에 걸 한 줄을 다시 정한다

### 상황
우리 블로그를 본 옆 팀이 이렇게 말했습니다 — "한 줄 소개만 봐서는 무슨 블로그인지 모르겠는데?" 다시 정해야 합니다. 이번엔 팀원 전원이 각자 자기 안을 냅니다. 그런데 고칠 파일은 하나, 고칠 줄도 하나입니다.

- **할 일**: 같은 줄을 전원이 고쳐 보고, 방법을 바꿔 한 번 더
- **알아낼 것**: 일을 어떻게 나누면 충돌이 줄어드는가
- **쓰는 개념**: 브랜치 · Pull Request · 병합 · 충돌 해결

### 1라운드 — 그냥 해보기

**문제 상황**: 팀장이 `about.txt`의 한 줄 소개를 빈 자리로 되돌려 push한다(`블로그 한 줄 소개: (다시 정하는 중)`). 전원이 `git pull`한 뒤 각자 브랜치를 만들어 그 한 줄을 자기 문구로 바꾼다. 커밋 → push → PR을 열고, 한 명씩 차례로 병합한다. 두 번째 사람부터 PR 화면이 어떻게 되는지 본다. 막힌 사람은 자기 컴퓨터에서 정리하고 다시 push한다. 충돌이 몇 번 났는지 센다.

**시도한 방법**
```
(팀장) about.txt 한 줄을 빈 자리로 되돌려 push
(전원) git pull

git switch -c 내브랜치
(about.txt 한 줄을 내 문구로 수정)
git add about.txt ; git commit -m "한 줄 소개 제안"
git push -u origin 내브랜치
→ PR 오픈 → 한 명씩 차례로 병합

# 두 번째 사람부터 충돌 발생 시
git switch main
git pull
git switch 내브랜치
git merge main
(파일을 열어 충돌 기호를 지우고 정리)
git add about.txt
git commit -m "충돌 해결: 한 줄 소개"
git push
```

**막혔던 점**
🔴 세 번째 사람부터 병합할 때 충돌이 나기 시작했다. 화면에 `CONFLICT (content): Merge conflict in about.txt`라는 문구가 떴는데 처음엔 이게 무슨 뜻인지 몰라서 당황했다.

**해결 과정 / 배운 점**
🟢 **해결 과정**: `git switch main` → `git pull`로 최신 상태를 받아온 뒤 내 브랜치에서 `git merge main`을 해서 충돌을 먼저 확인하고, 파일을 열어 기호를 지우고 정리한 다음 다시 push했다.

💡 **배운 점**: 같은 줄을 여러 명이 동시에 고치면 순서와 상관없이 나중에 병합하는 사람이 충돌을 떠안게 된다는 걸 알았다. PR을 늦게 열수록 최신 상태를 자주 받아와야 한다는 것도 깨달았다.

### 2라운드 — 줄여보기

**문제 상황**: 이번엔 소개를 문단으로 늘린다 — 한 사람당 한 줄씩, 모두 합쳐 소개 문단 하나를 만든다. 그 전에 팀이 상의해 **충돌을 줄일 방법**을 정한다. 담당 줄을 미리 나눠도, 파일을 나눠도, 올리는 순서를 정해도 된다. 무엇을 하든 팀이 정한다. 정한 방법대로 전원이 작업하고 병합한 뒤, 충돌 횟수를 다시 센다.

**시도한 방법**
1라운드에서 겪은 충돌을 근거로 "담당 줄을 미리 나눈다"는 규칙을 정하고 진행했다.
```
(팀 상의: 사람마다 몇 번째 줄을 쓸지 미리 배정)
git switch -c 내브랜치-2
(내가 맡은 줄만 추가)
git add about.txt ; git commit -m "소개 문단 - 내 줄 추가"
git push -u origin 내브랜치-2
→ PR → 병합
```

**막혔던 점 / 해결 과정**
🔴 **막혔던 점**: 담당 줄을 미리 나눴는데도, 한 사람이 실수로 자기 줄이 아닌 곳까지 같이 수정해서 올리는 바람에 충돌이 한 번 더 났다.

🟢 **해결 과정**: 담당 범위를 벗어난 부분은 다시 되돌리고, 각자 자기 줄만 건드리기로 다시 확인한 뒤 순서대로 병합했다.

**배운 점**
💡 우리 팀은 담당 줄을 미리 나눴을 때 충돌이 1라운드(전원이 겪음)에서 2라운드(단 한 번)로 확실히 줄었다. 역할을 미리 나누는 게 충돌을 완전히 없애진 못해도 크게 줄여준다는 결론을 내렸다.

### 끝나고 남는 것
- `about.txt` — 팀이 최종 합의한 한 줄 소개 + 소개 문단
- `team-rule.txt` — 두 라운드의 충돌 횟수가 모두 적혀 있다
- PR 탭에 두 라운드의 PR이 모두 병합되어 있고, 최소 한 명이 CONFLICT 글자를 실제로 봤다

## 미션 C: 글 상세 화면을 두 가지 방식으로 기록한다

### 상황
블로그에서 글 하나를 눌렀을 때 보이는 화면을 아직 아무도 안 적었습니다. 제목은 어디에, 본문은 어디에, 댓글은 어디에 붙는지 — 팀이 정해야 합니다. 두 조가 똑같은 내용을 똑같은 순서로 적습니다. 다른 것은 커밋을 쪼개는 방식 하나뿐입니다. 나중에 로그만 보고 서로 무엇을 했는지 맞혀 봅니다.

- **할 일**: 같은 작업을 커밋 단위만 다르게 → 로그로 맞히기
- **알아낼 것**: 커밋 하나에 무엇을 담아야 남이 읽을 수 있는가
- **쓰는 개념**: 커밋 · 커밋 히스토리 · 브랜치 · Pull Request

### 1단계 — 두 조로 나누기

**문제 상황**: 팀을 두 조로 나눈다. 두 조가 하는 일은 똑같다. 커밋을 쪼개는 방식만 다르다.
- **잘게조** — 커밋을 최대한 잘게 쪼갠다
- **한번에조** — 작업을 다 끝내고 커밋 한 번에 몰아넣는다

잘게조는 `screen-post-a.txt`, 한번에조는 `screen-post-b.txt`를 쓴다(충돌을 보는 미션이 아니라서 파일을 나눈다). 두 조 모두 아래 네 가지를 같은 순서로 한다.
1. 파일을 만들고 제목 줄을 적는다 — `글 상세 화면`
2. 화면에 들어갈 요소 3개를 적는다 (예: 글 제목 / 본문 / 댓글 목록)
3. 오타를 하나 고친다
4. 줄 하나를 지운다

**시도한 방법 — 잘게조**
```
git switch -c screen-a
(제목 줄 작성) → git add screen-post-a.txt → git commit -m "제목 줄 추가"
(요소 3개 작성) → git commit -m "화면 요소 3개 추가"
(오타 고침) → git commit -m "오타 수정"
(줄 하나 삭제) → git commit -m "불필요한 줄 삭제"
git push -u origin screen-a → PR → 병합
```

**시도한 방법 — 한번에조**
```
git switch -c screen-b
(제목 줄 + 요소 3개 + 오타 수정 + 줄 삭제를 한 번에 작업)
git add screen-post-b.txt
git commit -m "글 상세 화면 정리"
git push -u origin screen-b → PR → 병합
```

### 2단계 — 각자 방식대로

각자 브랜치에서 자기 조의 방식대로 작업하고 PR을 열어 병합한다. 커밋 메시지는 자기 말로 쓴다. 작업하는 동안 상대 조의 화면은 보지 않는다.

### 3단계 — 맞히기

**문제 상황**: 전원이 `git switch main` → `git pull` → `git log --oneline`. 상대 조의 **커밋 메시지만 보고** 그 사람이 무엇을 어떤 순서로 했는지 말한다. 파일은 열지 않는다. 1단계의 네 가지 중 몇 개나 맞혔는지 센다.

**시도한 방법**
```
git switch main
git pull
git log --oneline
```
잘게조의 로그는 네 줄로 각 작업이 명확히 구분됐고, 한번에조의 로그는 한 줄이라 무엇을 했는지 메시지만으로는 다 맞히기 어려웠다.

`commit-rule.txt`에 맞힌 개수와 "커밋 하나에 무엇을 담을지" 팀 합의문 3줄을 적어 커밋·push했다.

**막혔던 점**
🔴 한번에조의 커밋 메시지("글 상세 화면 정리") 하나만 보고는 오타를 고쳤는지, 줄을 지웠는지까지는 전혀 맞힐 수 없었다.

**배운 점**
💡 커밋 메시지는 "내가 무엇을 했는지 나만 아는 기록"이 아니라 "남이 파일을 안 열어도 알 수 있게 하는 기록"이어야 한다는 걸 확실히 느꼈다. 잘게 쪼갠 조는 로그만으로도 작업 순서가 다 읽혔다.

### 끝나고 남는 것
- `screen-post-a.txt`와 `screen-post-b.txt` — 내용은 거의 같은데 로그는 다르다
- `git log --oneline`에 두 방식이 눈에 띄게 다르게 보인다
- `commit-rule.txt`에 맞힌 개수와 합의문 3줄이 있다

## 미션 D: 블로그가 아닌 것이 병합됐다

### 상황
팀원 한 명이 신이 나서 기획서를 하나 더 올렸습니다. 그런데 열어 보니 상품 결제, 장바구니, 배송 조회... 우리가 만들기로 한 블로그와 아무 상관 없는 기능이 잔뜩 적혀 있습니다. 리뷰도 대충 승인돼서 이미 병합됐고, 전원의 컴퓨터에 들어왔습니다. 되돌려야 합니다.

- **할 일**: 사고를 만들고 → 되돌리고 → 규칙으로 남긴다
- **알아낼 것**: 팀 저장소에서 사고가 났을 때 무엇을 쓰고 무엇을 쓰면 안 되는가
- **쓰는 개념**: 되돌리기 · 커밋 히스토리 · Pull Request · 병합

> **이 미션만 팀 저장소에서 되돌리기를 한다. 아래 절차를 순서대로만 따른다. 순서를 건너뛰면 팀원 전체가 엉킨다.**

### 1단계 — 사고를 만든다

**문제 상황**: 한 명이 `feature-shop.txt`를 만들어 블로그와 상관없는 기능을 5줄 이상 적고(상품 결제·장바구니·배송 조회·재고 관리·쿠폰 등) 브랜치 → PR을 연다. 나머지가 일부러 그냥 승인해서 병합한다(사고 상황을 만드는 것이 목적). 전원이 `git switch main` → `git pull`. 모두의 컴퓨터에 그 파일이 들어온 것을 눈으로 확인한다.

**시도한 방법**
```
git switch -c feature-shop
(feature-shop.txt에 상품 결제/장바구니/배송 조회/재고 관리/쿠폰 등 5줄 이상 작성)
git add feature-shop.txt ; git commit -m "쇼핑 기능 기획서 추가"
git push -u origin feature-shop
→ PR 오픈 → (나머지 팀원) 그냥 승인 → 병합

(전원)
git switch main
git pull   # feature-shop.txt가 내 컴퓨터에도 들어온 것 확인
```

### 2단계 — 되돌린다

**문제 상황**: `git log --oneline`으로 되돌릴 커밋의 해시를 찾는다. 팀이 함께 보면서 한 명이 실행한다. `git log --oneline`을 다시 쳐서 잘못된 커밋이 사라졌는지, 아니면 그대로 있고 줄이 하나 늘었는지 팀이 함께 확인한다. 나머지 전원이 `git pull`로 되돌린 결과를 받아온다.

**시도한 방법**
```
git log --oneline                # 되돌릴 커밋 해시 확인
git revert <해시>
git push

git log --oneline                # 잘못된 커밋은 남아있고, 되돌리는 커밋이 새로 하나 늘었다

(나머지 전원)
git pull
(feature-shop.txt가 사라졌는지 각자 확인)
```

**막혔던 점**
🔴 `git revert`와 `git reset`이 뭐가 다른지 처음엔 구분이 안 됐다. `reset`을 쓰면 기록 자체가 사라진다는 걸 찾아보고 나서야, 이미 팀원 전체가 pull 받은 상황에서는 `reset --hard`를 쓰면 안 되는 이유를 실감했다.

**배운 점**
💡 팀 저장소에서는 "지우는 것"보다 "지웠다는 사실 자체를 새 커밋으로 남기는 것"이 안전하다는 걸 알았다. `revert`는 기록을 보존하면서 되돌리기 때문에 다른 사람의 `pull`을 망가뜨리지 않는다는 게 핵심이었다.

### 3단계 — 규칙으로 남긴다

`team-rule.txt`에 세 가지를 적어 커밋·push한다.
1. 우리가 쓴 명령과 기록이 어떻게 됐는지
2. 팀 저장소에서 쓰지 않기로 한 것과 그 이유
3. 이런 PR을 병합 전에 걸러내려면 리뷰에서 무엇을 봐야 하는지

> `git reset --hard`는 팀 저장소에서 절대 쓰지 않는다. 남의 작업까지 날린다. 세기 차이를 직접 보고 싶으면 개인 저장소에서 실험한다.

### 끝나고 남는 것
- `feature-shop.txt`가 전원의 컴퓨터에 한 번 들어왔다가 사라졌다
- `git log --oneline`에 잘못된 커밋과 되돌린 커밋이 둘 다 남아 있다
- `team-rule.txt`에 세 가지가 모두 적혀 있다

## 미션 E: 출시 로드맵을 두고 갈라진다

### 상황
블로그를 언제 무엇까지 만들지 3단계로 정하기로 했습니다. 1차는 글 발행, 2차는 댓글, 그리고 3차를 무엇으로 할지에서 팀 의견이 갈립니다. 그런데 한 조는 다른 조가 이미 3차를 고쳐 병합한 것을 모른 채 작업을 시작합니다. 브랜치를 딴 시점이 어긋난 것입니다.

- **할 일**: 갈라진 시점을 일부러 어긋나게 만들고 해결한다
- **알아낼 것**: 브랜치를 따는 시점이 다르면 무슨 일이 생기는가
- **쓰는 개념**: 브랜치 · 병합 · Pull Request · 충돌 해결

### 1단계 — 시점을 어긋나게 만든다

**문제 상황**: 팀장이 `roadmap.txt`를 만들어 세 줄을 적고 push한다(`1차 출시: 글 발행과 글 목록` / `2차 출시: 댓글` / `3차 출시: (정하는 중)`). 전원이 `git pull`로 받는다. 팀을 두 조로 나누고, 지금 두 조 모두 같은 지점에서 브랜치를 만든다. 먼저조가 `roadmap.txt`의 3번째 줄을 자기 안으로 고쳐 커밋 → push → PR → 병합한다. 나중조는 `git pull`을 하지 않은 채 자기 브랜치에서 같은 3번째 줄을 다른 안으로 고쳐 커밋 → push → PR을 연다. 나중조는 PR 화면이 뭐라고 하는지 읽고 그대로 적는다.

**시도한 방법**
```
(팀장) roadmap.txt 세 줄 작성 → push
(전원) git pull

(두 조 모두, 같은 지점에서)
git switch -c roadmap-먼저 / git switch -c roadmap-나중

(먼저조)
(roadmap.txt 3번째 줄을 "3차 출시: 검색 기능"으로 수정)
git add roadmap.txt ; git commit -m "3차 출시 항목 확정: 검색 기능"
git push -u origin roadmap-먼저 → PR → 병합

(나중조 — git pull 하지 않은 채)
(roadmap.txt 3번째 줄을 "3차 출시: 태그 기능"으로 수정)
git add roadmap.txt ; git commit -m "3차 출시 항목 제안: 태그 기능"
git push -u origin roadmap-나중 → PR 오픈
→ PR 화면에서 "그냥 병합할 수 없다"는 안내를 그대로 옮겨 적음
```

**막혔던 점**
🔴 PR 화면에 `This branch has conflicts that must be resolved`라는 문구가 떴는데, 처음엔 왜 자동으로 병합이 안 되는지 이해가 안 됐다. 분명 같은 파일을 고쳤을 뿐인데 왜 막히는지 헷갈렸다.

### 2단계 — 나중조가 해결한다

**시도한 방법**
```
git switch main
git pull
git switch roadmap-나중
git merge main
(파일을 열어 충돌 기호를 지우고 정리 — 3차 출시 내용을 팀이 실제로 합의해서 정함)
git add roadmap.txt
git commit -m "3차 출시 항목 합의: 검색+태그 기능"
git push
```
push한 뒤 PR 화면이 어떻게 바뀌는지 보고 병합했다.

> 3차 출시 내용은 팀이 실제로 합의해서 정한다. 한쪽을 지워도, 둘을 합쳐도 된다 — 다만 왜 그렇게 정했는지를 3단계에 적는다.

**해결 과정 / 배운 점**
🟢 **해결 과정**: 두 조가 낸 안(검색 기능, 태그 기능) 중 하나만 고르지 않고, 팀 논의 끝에 "검색+태그 기능"으로 둘 다 합치기로 했다. `main`을 merge해서 충돌 부분을 직접 문장으로 다시 써서 해결했다.

💡 **배운 점**: 브랜치를 딴 시점이 다르면(먼저조가 병합한 뒤에 나중조가 그 사실을 모른 채 작업하면) 반드시 최신 상태를 pull 받고 시작해야 한다는 걸 알았다. 두 안이 서로 배타적이지 않다면 "합치기"도 좋은 선택이라는 것도 이번에 알게 됐다.

### 3단계 — 규칙으로 남긴다

`git log --oneline`으로 기록 모양을 확인하고 `branch-rule.txt`에 세 줄을 적어 커밋·push한다.
1. 브랜치를 만들기 전에 무엇을 해야 하는가
2. 우리 팀의 브랜치 이름 규칙
3. 나중조가 본 화면 문구를 그대로

### 끝나고 남는 것
- `roadmap.txt` 3번째 줄이 팀이 합의한 내용으로 채워져 있다
- 나중조의 PR 화면에서 그냥 병합할 수 없다는 안내를 실제로 봤고, 해결한 뒤 병합됐다
- `branch-rule.txt`에 세 줄이 모두 있다

# 다섯 미션을 다 풀어보고 나서

- 미션마다 같은 브랜치 → PR → 리뷰 → 병합 흐름을 쓰지만, **무엇을 관찰하게 만드는지**가 다 달랐다. (A: 충돌을 줄이는 방법 / B: 판정 가능한 리뷰 기준 / C: 커밋 단위가 남기는 정보량 / D: 팀 저장소에서 안전하게 되돌리기 / E: 브랜치를 딴 시점의 중요성)
- 다섯 미션을 통틀어 가장 인상 깊었던 것: 💡 미션 D에서 `git reset --hard`가 팀원 전체의 작업을 날릴 수 있다는 걸 직접 목격한 것이다. "이건 절대 쓰지 않는다"는 규칙이 왜 필요한지 이론이 아니라 상황으로 이해됐다.
- 만약 우리 팀이 다른 미션을 배정받았다면 가장 헤맸을 것 같은 미션: 🔴 미션 E일 것 같다. 브랜치를 딴 시점의 차이 때문에 생기는 충돌은 평소엔 눈에 잘 안 보이다가 병합 시점에야 터지는 문제라, 원인을 못 찾고 한참 헤맸을 것 같다.
