> 이 글은 **자율 실습 · 12문제**(개인 실습) 중 **Lv.1 — 기본 변형(5문제)**을 기록한 devlog입니다.
> AI(Claude Code)가 내 블로그 파일을 직접 고치는 상황에서, 먼저 "되돌리는 법"부터 익힌다.
> 문제마다 `문제 상황 → 시도한 방법 → 막혔던 점 → 해결 과정 → 배운 점` 순서로 정리했다.

> 문제 원문: [Claude Artifact — 되돌릴 수 있어야 시킨다](https://claude.ai/code/artifact/96689c97-96f9-42d5-be46-3666a79cac73)

## 시작 전 공통 규칙

⚠️ AI가 내 진짜 블로그 파일을 직접 고친다. 커밋해 둔 지점이 없으면 돌아갈 곳이 없다.

- 시키기 전에 커밋한다. 시작할 때마다 `git status`로 clean인지 확인한다.
- 모드를 확인한다. 입력창 아래 `⏸ manual mode on`이 보이는지 본다. `⏵⏵`로 시작하면 안 묻고 고치는 모드라서 Shift+Tab(안 되면 Alt+M)으로 바꾼다.

💡 되돌리기는 "git이 그 파일을 아는가"로 세 갈래로 갈린다.

- **원래 있던 파일이 고쳐졌다 (커밋 전)** → `git restore <파일>` (여러 개면 `git restore .`)
- **없던 파일이 새로 생겼다** → `restore`로는 안 된다. `git clean -n -d`로 목록만 먼저 보고, `git clean -f -d <이름>`으로 이름을 적어서 지운다.
- **이미 커밋됐다** → `git log --oneline`으로 맨 위 커밋(방금 만든 것)의 앞 7글자를 확인하고 `git revert --no-edit <7글자>`.

🚨 `git clean`으로 지운 것은 되살릴 수 없다. `-n`은 보기만, `-f`는 진짜 지움, `-d`를 붙여야 폴더까지 지운다. 반드시 이름을 적어서 지운다.

⚠️ `revert`에서 글자로 가득 찬 낯선 화면이 뜨면 `--no-edit`을 빠뜨린 것이다 — Esc → `:q!` → Enter (`q`로는 안 나가진다). 뭔가를 고르라는 화면이 뜨면 충돌이 난 것이므로 `git revert --abort`로 통째로 취소한다.

## Lv.1 — 기본 변형 (5문제)

## 1. 한 줄 지시로 학습 노트 한 편 더 쓰기

### 문제 상황
한 줄로만 지시해서 다른 주제(아직 글로 안 쓴 것)로 학습 노트를 한 편 더 쓰게 한다. 규칙을 하나도 말하지 않았는데 `_posts/`에 새 글이 생기고, 파일명·머리말·날짜가 맞고, push 후 블로그에서 그 글이 보이는지 확인한다.

### 시도한 방법
```
<주제>로 학습 노트 글 하나 써줘
```
쓴 다음 커밋과 push까지 시키고 브라우저로 직접 확인한다.

### 막혔던 점
🔴 규칙을 하나도 안 알려줬는데도 파일명·머리말이 맞을지 확신이 안 서서, 결과가 나오기 전까지 계속 불안했다.

### 해결 과정
🟢 결과가 나온 뒤 `_posts/` 경로와 파일명, front matter를 직접 열어 CLAUDE.md 규칙과 하나씩 대조했다.

### 배운 점
💡 규칙을 매번 말로 안 해도 `CLAUDE.md`가 이미 규칙 저장소 역할을 한다는 걸 눈으로 확인했다.

## 2. CLAUDE.md에 글 내용 규칙 하나 추가하기

### 문제 상황
저장소 맨 위 `CLAUDE.md`에 글 내용 규칙을 하나 더 넣는다(예: "글 맨 끝에 요약을 3줄로 넣는다"). 넣은 뒤 `/clear`하고 새 글을 하나 쓰게 해서 그 규칙이 지켜지는지 확인한다.

### 시도한 방법
```
## 글 내용 규칙

- 맨 앞에 무엇을 배웠는지 한 문장으로 쓴다.
- (여기에 한 줄 추가)
- 맨 끝에 "아직 헷갈리는 것"을 한 줄 넣는다.
```
규칙 추가 → `/clear` → 새 글 작성 지시 → 결과 확인. 안 지켜졌다면 문장을 고쳐서 다시 해본다.

### 막혔던 점
🔴 처음 넣은 문장이 "잘 정리해서 넣어줘"처럼 애매해서 결과물에 규칙이 반영됐는지 판단하기 어려웠다.

### 해결 과정
🟢 "3줄로 넣는다"처럼 숫자·형식이 들어간 문장으로 고쳐 다시 시도하니 결과에서 바로 확인이 됐다.

### 배운 점
💡 안 지켜지는 규칙은 대개 문장이 애매하다. "잘"·"보기 좋게" 같은 표현은 AI도 판정 기준을 못 잡는다.

## 3. 되돌리기 세 갈래 직접 확인하기

⭐ 자율 실습 중 가장 실용적인 문제.

### 문제 상황
같은 "AI가 파일을 건드린" 상황을 세 갈래로 나눠 직접 겪어본다.

1. `index.md`를 고치라고 시킨다(커밋 안 함) → `git restore index.md` → 결과 확인
2. `scratch.md`라는 새 파일을 만들라고 시킨다 → `git restore .` → 결과 확인
3. `git clean -n -d`로 목록만 먼저 보고 `scratch.md`만 있는지 확인한 뒤 `git clean -f -d scratch.md`로 지운다
4. `scratch.md`를 다시 만들고 커밋한 뒤, `git log --oneline`으로 앞 7글자를 메모하고 `git revert --no-edit <7글자>`로 되돌린다

세 결과가 왜 달랐는지 한 줄로 적고, 끝나면 저장소를 clean 상태로 정리한다.

### 시도한 방법
```
git switch main   # 시작 전 clean 확인
git status

# 1) 있던 파일 수정 → restore
(index.md 수정 지시) 
git restore index.md
git status

# 2) 새 파일 생성 → restore .
(scratch.md 생성 지시)
git restore .
git status

# 3) clean으로 지우기
git clean -n -d
git clean -f -d scratch.md

# 4) 커밋된 것 → revert
(scratch.md 다시 생성)
git add scratch.md
git commit -m "실험용 파일 추가"
git log --oneline
git revert --no-edit <메모한 7글자>
```

⚠️ `error: your local changes would be overwritten`이 나오면 고친 것을 커밋하지 않은 상태다. `git status`로 확인하고 커밋하거나 `git restore .`로 정리한 뒤 다시 한다.

### 막혔던 점
🔴 2번(새 파일)에서 `git restore .`를 쳤는데 `scratch.md`가 그대로 남아 있어서 처음엔 명령이 안 먹힌 줄 알았다. restore는 "git이 이미 아는 파일"에만 통하고, 추적 안 되는(Untracked) 새 파일에는 안 통한다는 걸 그때는 몰랐다.

### 해결 과정
🟢 매 단계마다 `git status`를 먼저 찍어서 그 파일이 어느 칸(Untracked / Changes not staged / 이미 커밋됨)에 있는지 확인한 다음, 칸에 맞는 명령(restore / clean / revert)을 골랐다.

### 배운 점
💡 `git status`에서 파일이 어느 칸에 있는지가 답이다 — 추적 안 되는 파일과 고쳐진 파일은 다른 칸이고, 이미 커밋된 것은 아예 안 나온다.

> (...) 1·2·4의 결과가 실제로 어떻게 달랐는지 직접 겪은 내용으로 채우기

### 확인 체크리스트
- [ ] 1·2·4의 결과를 각각 적었다
- [ ] 세 결과가 서로 다르다
- [ ] 왜 다른지를 한 줄로 적었다
- [ ] `git status`가 다시 clean이다

## 4. 넓게 묻고 좁혀서 다시 묻기

### 문제 상황
내가 지금 실제로 막혀 있는 것 하나를 골라 두 번 묻는다. 먼저 넓게 묻고(예: "깃허브 페이지 알려줘"), 같은 것을 내 상황을 최소 두 가지 넣어 좁혀서 다시 묻는다. 두 답을 항목별로 판정한다.

### 시도한 방법
```
(넓은 질문 예)
깃허브 페이지 알려줘

(좁힌 질문 구조)
(무엇을 했는지)를 했는데,
지금 (어떤 상태)이고,
(무엇을 하고 싶은지) 하고 싶어요. 어떻게 하면 되죠?
```
두 답을 나란히 놓고 아래를 O/X로 판정한다.
- 답에 배운 적 없는 것이 섞였나
- 답이 내 상황에 맞나
- ⭐ 답이 맞는지 확인할 수 있나

### 막혔던 점
🔴 넓게 물었더니 답이 너무 일반적이라 내 상황(무엇을 이미 했는지, 지금 어떤 화면인지)에 맞는지 판단이 안 됐다.

### 해결 과정
🟢 "무엇을 했는지"와 "무엇을 하려는지" 두 가지를 문장에 넣어 다시 물으니, 답이 내 상황에 맞는 구체적인 단계로 바뀌었다.

### 배운 점
💡 좁혀 묻는 건 길게 쓰는 게 아니라 관계없는 내용을 빼는 것이다. 좁힐수록 "맞는지 확인 가능한" 답이 나온다.

## 5. CLAUDE.md 규칙 하나 지우고 결과 확인하기

### 문제 상황
`CLAUDE.md`에서 규칙 하나만 지우고(다른 것은 그대로) 새 글을 쓰게 해서 그 규칙이 안 지켜지는지 확인한다.

### 시도한 방법
```
git add CLAUDE.md
git commit -m "규칙 실험 전 상태"   # 시작 전

(규칙 하나만 삭제)
/clear
(새 글 작성 지시)

git restore CLAUDE.md               # 끝나고 복구
```

⭐ 손으로 복사해 두지 않는다 — 커밋해 두면 되돌릴 수 있다는 것이 이 문제의 요점이다.

### 막혔던 점
🔴 어떤 규칙을 빼야 차이가 눈에 보일지 고르기 애매했다. 추상적인 규칙을 빼면 지켜졌는지 안 지켜졌는지 판단 자체가 어려웠다.

### 해결 과정
🟢 날짜 형식·파일명처럼 판정이 쉬운 규칙을 골라 지우니 결과에서 차이가 바로 보였다.

### 배운 점
💡 "그래도 지켜졌다"도 좋은 결과다. 왜 그랬을지 직접 생각해서 적는 것이 이 문제의 답이 된다.

## Lv.1 다섯 문제를 풀어보고 나서

> (...) 다섯 문제를 전부 마친 뒤, 가장 오래 걸린 문제와 그 이유, 되돌리기 세 갈래 중 실제로 가장 자주 쓰게 된 것을 여기에 정리한다.

## 더 학습하면 좋은 개념

- **Git reflog** — `revert`/`restore`/`clean`으로도 못 되돌리는 상황(예: 브랜치를 잘못 지웠을 때)에서 최후의 수단이 된다. HEAD가 가리켰던 지점의 기록을 남겨두기 때문에, 3번 문제(되돌리기 세 갈래)의 다음 단계로 알아두면 좋다.
- **프롬프트 엔지니어링 — Few-shot / 예시 기반 지시** — `CLAUDE.md`에 "판정 가능한 문장"을 넣는 연습(2번 문제)의 다음 단계로, 규칙을 문장이 아니라 예시로 보여주면 더 안정적으로 지켜지는 경우가 많다.
